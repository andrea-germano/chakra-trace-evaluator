# Short-burst incast, v2: the amortisation of the incast transient, measured on
# a grid CONGRUENT with the long sweep so the two are directly comparable.
#
# Same three topologies (T2.1/T3/T4 = fan-in 1/2/4), same seven buffers
# (8..64 MiB), same fabric configs (reused verbatim from incast_sweep), same
# DCQCN. The only knob that moves against the long 16reqs/512prompt run is the
# burst length: one request of 512/256/128/64 prompt tokens, i.e. a
# serialisation floor of 8.5/4.2/2.1/1.1 ms per receiver against 135.6 ms.
# Everything in the workload scales with the token count EXCEPT the CC
# convergence transient (~0.27 ms for DCQCN), so the incast term's share of the
# floor must rise as the burst shrinks; the fan-in-1 control must stay flat.
#
# 32-token runs were tried and REMOVED: the fan-in-1 control alone leaves 284%
# of the floor there (fixed per-flow costs, link efficiency 26% with no
# congestion at all), so nothing at that length is attributable to incast.
# The 64-token row, once measured, turned out below resolution as well (the
# control leaves 98% of the floor); it is KEPT as the measured resolution
# limit of the harness, drawn hollow by incast_compare and never quoted.
# 128 tokens is the deepest quotable point.
#
# One cell is EXCLUDED, not forgotten: T4_bx100_dcqcn_buf8 at 512 tokens
# livelocks deterministically (same cell as the cc_sweep's known-unobtainable
# point; reproduced twice on this workload too, stuck at 15/20 ranks).
